# 代理模式：通俗入门

> **第一层「入门」材料**：重点是「为什么访问一个对象需要经过另一个对象」。
> 静态代理、动态代理、远程代理、缓存代理的工程实现见 [README.md](README.md)。
>
> 可运行代码：[beginner/BeginnerDemo.java](beginner/BeginnerDemo.java)

---

## 1. 一句话说人话

**代理就是：不让你直接碰目标对象，而是先经过一个「同款替身」，
替身负责拦一下、查一下、等一等，再把请求转给目标。**

### 什么需求会让开发者想到它

系统里有一份 50MB 的销售报表，只有管理员能看。第一版：

```java
class ReportViewer {
    void open(User user) {
        RealReport report = new RealReport();   // 先加载 50MB
        if (!user.admin) { 拒绝; return; }
        report.display();
    }
}
```

问题有两个：

- 访客被拒绝前，**50MB 已经加载完了**；
- 新加的导出入口忘了鉴权，**访客直接把报表导出去了**。

代理要解决的是：**访问控制、延迟加载、访问记录这些事，
不该由每个调用方各写一遍，也不该塞进真实报表里。**

## 2. 先看不使用代理的代码

完整版在 [BeginnerDemo.java](beginner/BeginnerDemo.java) 的 `before()`：

```java
class ReportViewer {
    void open(User user) {
        OldRealReport report = new OldRealReport();   // 先加载
        if (!user.admin) { ... return; }
        report.display();
    }
}

class ExportService {
    void export(User user) {
        OldRealReport report = new OldRealReport();
        report.display();                             // 忘了鉴权
        ...
    }
}
```

真实输出：

```text
    [报表] 加载 50MB 数据...
    拒绝 访客：没有报表权限
    [报表] 加载 50MB 数据...
    [报表] 显示销售明细
    [报表] 加载 50MB 数据...
    [报表] 显示销售明细
    导出完成，操作人：访客
```

---

## 3. 为什么原来的设计不方便

### 3.1 谁依赖谁

```text
ReportViewer  ──▶ RealReport（直接 new、直接调用）
ExportService ──▶ RealReport（同样直接 new）
```

每个入口都同时依赖真实对象和访问规则。

### 3.2 问题出在哪

| 问题 | 原因 | 后果 |
|---|---|---|
| 访客也加载 50MB | 加载在鉴权之前 | 浪费内存和 IO |
| 访客能导出 | 导出入口漏了鉴权 | 数据泄露 |
| 加载多次 | 每个入口 new 一次 | 重复成本 |
| 规则分散 | 每个入口各写一遍 | 漏一处就是事故 |

### 3.3 为什么不能在 RealReport 里加鉴权

可以在 `display()` 里加，但那样真实报表就同时承担了「显示数据」和「访问控制」，
职责混在一起；而且不同入口可能需要不同的控制策略（缓存、日志、限流），
全塞进 RealReport 会让它越来越难维护。

## 4. 从问题推导出设计

### 第 1 步：抽出客户端使用的接口

```java
interface Report {
    void display(User user);
}
```

**为什么？** 客户端只认「能显示报表」，不关心拿到的是真实对象还是替身。
**不加会怎样？** 客户端必须知道 `ReportProxy` 这个具体类型，代理就失去了透明性。

### 第 2 步：代理实现同一接口，并持有真实对象

```java
class ReportProxy implements Report {
    private RealReport real;

    public void display(User user) {
        if (!user.admin) { 拒绝; return; }
        if (real == null) {
            real = new RealReport();   // 第一次真正需要时才加载
        }
        real.display(user);
    }
}
```

**为什么代理自己创建真实对象？** 因为「延迟加载」要求真实对象在需要时才出现；
代理持有创建权，才能控制时机。
**不加会怎样？** 调用方要么提前 new（白加载），要么自己判断（重复逻辑）。

### 第 3 步：客户端只拿接口

```java
Report report = new ReportProxy();
report.display(guest);   // 拒绝，且没有加载
report.display(admin);   // 加载一次，显示
report.display(admin);   // 复用，不再加载
```

最终关系：

```text
客户端 ──▶ Report（接口）
              ▲
              │ 实现
        ReportProxy ──持有/延迟创建──▶ RealReport
              │
              └── 鉴权、访问日志
```

真实输出（节选）：

```text
  访客打开：
    拒绝 访客：没有报表权限（未加载数据）
  管理员打开：
    [报表] 加载 50MB 数据...
    [代理] 记录访问日志：管理员
    [报表] 显示销售明细（管理员）
  管理员再导出：
    [代理] 记录访问日志：管理员
    [报表] 显示销售明细（管理员）
  访客导出：
    拒绝 访客：没有报表权限（未加载数据）

  真实报表一共加载了 1 次。
```

## 5. 用执行过程理解代码

以管理员第二次调用为例：

1. 客户端调 `report.display(admin)`；
2. 进入 `ReportProxy.display`；
3. 鉴权通过；
4. `real != null`，不重新创建；
5. 记录访问日志；
6. 调 `real.display(admin)`，显示数据。

**最容易混淆的地方**：

```java
private RealReport real;
```

代理和装饰器都持有目标，但目的不同：装饰器的 `inner` 通常由外部传入，
强调「叠加功能」；代理的 `real` 往往由代理自己创建，强调「控制访问」。
实现很像，**意图不同**。

## 6. 改造前后对比

### 6.1 新增一个「打印」入口

| | 改造前 | 改造后 |
|---|---|---|
| 新增入口 | 自己 new + 自己鉴权 | 注入 `Report`，直接调 |
| 漏鉴权风险 | 高 | 代理统一处理 |
| 访客是否加载 | 取决于写法，容易先加载 | 不会加载 |
| 真实对象加载次数 | 每个入口一次 | 一次（复用） |

### 6.2 代价

- 多一层间接，所有调用都经过代理；
- 代理写错会影响所有入口；
- 延迟加载会引入状态（是否已加载），要考虑并发；
- 如果对象很便宜、也没有访问控制需求，代理只是多余包装。

### 6.3 什么时候不需要

- 对象创建很便宜，访问也不需要控制；
- 只有一个调用入口，直接写鉴权更简单；
- 需要的是「加功能」而不是「控访问」——那是装饰器。

## 7. 适用边界

### 适合

- **保护代理**：鉴权、限流、审计；
- **虚拟代理**：延迟加载大对象（图片、报表、远程资源）；
- **远程代理**：本地对象代表远程服务（RPC 存根）；
- **缓存代理**：命中缓存就不调用真实对象；
- **日志/监控代理**：统一记录调用。

### 不适合

- 对象很便宜、访问没有额外规则；
- 代理开始承载业务逻辑；
- 为了「看起来解耦」而给每个类都加代理。

### 容易混淆

| 模式 | 目的 | 关键区别 |
|---|---|---|
| **装饰器** | 给对象**加功能** | 装饰器接收现成对象，强调叠加；代理常自己创建目标，强调控制 |
| **适配器** | **转换接口** | 适配器改变接口；代理保持同一接口 |
| **外观** | **简化多个子系统** | 外观是「多对一」入口；代理是「一对一」替身 |
| **中介者** | 对象间**双向通信** | 中介者协调多个同事；代理代表一个目标 |

> 动态代理（JDK `Proxy`、CGLIB）只是「生成代理类」的技术手段，
> 不是代理模式的必要条件。手写一个实现同一接口的类，同样是代理。

## 8. 小练习

### 练习 1（场景判断）

一个 `StringUtils.trim()` 是纯函数，调用它没有任何权限、缓存或远程开销。
需要代理吗？

**参考答案**：不需要。代理的价值来自「控制访问」；纯函数没有需要控制的访问，
加代理只会多一层调用。

### 练习 2（解释设计原因）

为什么 `ReportProxy` 要实现 `Report` 接口，而不是直接提供 `openReport()` 方法？

**参考答案**：实现同一接口，客户端才能在不改代码的情况下用代理替换真实对象
（`Report report = new ReportProxy()`）。如果代理有自己的方法名，
调用方就必须知道「现在用的是代理」，代理的透明性就没了。

### 练习 3（并发思考）

如果两个线程同时第一次调用 `display()`，`if (real == null) real = new RealReport();`
可能出什么问题？怎么改？

**参考答案**：两个线程可能都看到 `null`，各自创建一个真实报表，导致重复加载，
后创建的覆盖先创建的。可以加锁、用双重检查、或借助 Holder/并发容器保证只创建一次。
**代理模式本身不解决并发问题，线程安全要单独设计。**

## 9. 读完之后

你应该能回答：

1. 代理为什么存在？——在不改目标对象的前提下控制对它的访问。
2. 原始实现的问题？——鉴权/加载散落、访客白加载、漏鉴权导致泄露。
3. 每个角色为什么存在？——接口统一类型，代理控制访问，真实对象只负责业务。
4. 怎么协作？——客户端调接口 → 代理鉴权/延迟创建/记录 → 转发给真实对象。
5. 新场景要不要用？——看是否存在访问控制、延迟加载、远程/缓存等「控制」需求。
