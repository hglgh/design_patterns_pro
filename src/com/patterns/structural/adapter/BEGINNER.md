# 适配器模式：通俗入门

> **第一层「入门」材料**：重点是「两个本来不兼容的接口，怎么不动任何一边就接上」。
> 类适配器/对象适配器、双向适配器等工程细节见 [README.md](README.md)。
>
> 可运行代码：[beginner/BeginnerDemo.java](beginner/BeginnerDemo.java)

---

## 1. 一句话说人话

**适配器就是：两样东西本来插不上，中间加一个转换头，让它们不用改造自己就能合作。**

### 什么需求会让开发者想到它

系统要接支付。业务代码习惯这样写：

```java
payment.pay("ORDER-1001", 199.00);   // 订单号 + 元
```

但采购来的老支付 SDK 只有这个方法：

```java
sdk.doPay(19900, "ORDER-1001");      // 分 + 订单号，顺序还相反
```

老 SDK 是厂商的，**改不了**；业务代码已经遍布各处，**不想全改**。
于是需要一层转换：把「元」换成「分」，把参数顺序摆正。

这就是适配器要解决的场景：**接口不兼容，但两边都不能/不该为对方改变。**

---

## 2. 先看不使用适配器的代码

完整版在 [BeginnerDemo.java](beginner/BeginnerDemo.java) 的 `before()`：

```java
OldPaySdk sdk = new OldPaySdk();

// 下单支付：自己把元换成分
int cents = (int) Math.round(199.00 * 100);
sdk.doPay(cents, "ORDER-1001");

// 退款：同一个换算，又写了一遍
int refundCents = (int) Math.round(59.90 * 100);
sdk.doPay(refundCents, "ORDER-1002");
```

真实输出：

```text
  [老 SDK] 扣款 19900 分，订单 ORDER-1001
  [老 SDK] 扣款 5990 分，订单 ORDER-1002
```

看起来能跑，问题在「每个调用方都要懂老 SDK 的单位和参数顺序」。

---

## 3. 为什么原来的设计不方便

### 3.1 谁依赖谁

```text
下单业务 ──直接依赖──▶ OldPaySdk.doPay(int 分, String 订单号)
退款业务 ──直接依赖──▶ OldPaySdk.doPay(int 分, String 订单号)
```

业务代码依赖的是**厂商的接口形状**，而不是自己想要的「支付」概念。

### 3.2 问题出在哪

| 变化 | 改造前要改哪里 | 后果 |
|---|---|---|
| 老 SDK 升级，方法改名 | 所有调用点 | 一处漏改就编译失败 |
| 金额单位从分改成厘 | 所有换算 | 漏一处就金额错误 |
| 再接微信支付 | 业务方法加 if/else | 业务代码越来越懂支付渠道 |

### 3.3 为什么不能「让老 SDK 实现我们的接口」

因为 SDK 是第三方 jar，源码不在你手里；即使能改，也不应该为了自己的业务
去改厂商代码——下次升级就冲突了。

**为什么不能「把业务代码改成用分」？** 可以，但业务语义会变得别扭：
订单金额本来是元，为了迁就 SDK 全系统改成分，是把外部模型的复杂度引进业务。

## 4. 从问题推导出设计

### 第 1 步：定义业务真正想要的接口

```java
interface PaymentGateway {
    void pay(String orderNo, double amountYuan);
}
```

**为什么需要它？** 业务只想表达「为这个订单收这么多钱」，单位和参数顺序应符合业务直觉。
**不加会怎样？** 业务代码继续直接面对 SDK 的 `int cents, String orderId`。

### 第 2 步：写一个适配器，持有老 SDK

```java
class LegacyPayAdapter implements PaymentGateway {
    private final OldPaySdk sdk;

    public void pay(String orderNo, double amountYuan) {
        int cents = (int) Math.round(amountYuan * 100);
        sdk.doPay(cents, orderNo);
    }
}
```

**为什么是「持有」而不是「继承」？** 持有（对象适配器）不占用唯一的继承位，
也能适配 `final` 类；继承（类适配器）要求 SDK 可继承，且 Java 只能单继承。
**不增加它会怎样？** 换算逻辑继续散落在每个调用方。

### 第 3 步：业务方法只依赖接口

```java
void checkout(PaymentGateway gateway, String orderNo, double amountYuan) {
    gateway.pay(orderNo, amountYuan);
}
```

**为什么？** 业务不再知道老 SDK、微信、支付宝的区别。
**不加会怎样？** 每接一个渠道，`checkout` 就要加一个分支。

最终关系：

```text
checkout ──▶ PaymentGateway（业务期望的接口）
                  ▲
                  │ 实现
           LegacyPayAdapter ──持有──▶ OldPaySdk（不能改）
```

真实输出（节选）：

```text
  [老 SDK] 扣款 19900 分，订单 ORDER-1001
  [微信支付] 收款 59.9 元，订单 ORDER-1002
  —— 新增支付宝：只加一个适配器，checkout 不改 ——
  [支付宝] 收款 88.8 元，订单 ORDER-1003
```

## 5. 用执行过程理解代码

`checkout(legacy, "ORDER-1001", 199.00)`：

1. `legacy` 的运行时类型是 `LegacyPayAdapter`；
2. 调 `gateway.pay(...)`，进入适配器；
3. 适配器把 `199.00` 元换算成 `19900` 分；
4. 调 `sdk.doPay(19900, "ORDER-1001")`，参数顺序也被摆正；
5. 老 SDK 打印扣款。

**最容易写错的一行**：

```java
int cents = (int) Math.round(amountYuan * 100);
```

`199.00 * 100` 在浮点里可能是 `19899.999...`，直接强转会变成 `19899`。
`Math.round` 先四舍五入再转 int，才是正确的分。适配器是把这类「两边语义差异」
集中处理的地方，写错一次会影响所有调用。

## 6. 改造前后对比

### 6.1 新增支付宝

| | 改造前 | 改造后 |
|---|---|---|
| 业务方法 | 加 `if ("alipay")` | **0 行修改** |
| 新增类 | 0（分支变多） | `AlipayAdapter` |
| 单位换算 | 每个调用点 | 只在适配器里 |
| 测试 | 业务方法要覆盖所有渠道 | 每个适配器单独测 |

### 6.2 代价

- 每个外部接口多一个适配器类；
- 多一层调用，调试时调用栈变长；
- 如果适配器里塞了业务规则（折扣、风控），它会变成第二个业务层；
- 如果两边接口本来就能统一，适配器是多余的。

### 6.3 什么时候不需要

- 你能直接修改厂商代码/旧类，让它实现新接口；
- 新旧接口本来就兼容，只是名字不同（改个名即可）；
- 只有一次调用，转换只有一行，包一个类反而更难读。

## 7. 适用边界

### 适合

- 第三方 SDK、遗留系统、外部协议与本地接口不兼容；
- 同一业务需要对接多个外部实现，希望业务代码不感知差异；
- 老接口不能改（无源码、升级冲突、被多个系统共用）。

### 不适合

- 能改源码、能统一接口；
- 接口差异只是命名，没有语义转换；
- 适配器承担了本不属于它的业务逻辑。

### 容易混淆

| 模式 | 目的 | 与适配器的区别 |
|---|---|---|
| **装饰器** | 在不改接口的前提下**增加功能** | 装饰器和目标实现同一接口，接口不变；适配器**改变**接口 |
| **代理** | **控制**对目标的访问 | 代理和目标是同一接口；适配器是把一个接口转成另一个 |
| **外观** | 把多个子系统**简化**成一个入口 | 外观是「多对一」简化；适配器是「一对一」转换 |

> 判断口诀：**接口变了是适配器，接口没变加功能是装饰器，接口没变控访问是代理。**

## 8. 小练习

### 练习 1（场景判断）

系统里有一个 `DateUtil.format(Date)`，新代码想要 `format(LocalDate)`。
两者都是你自己的代码。需要适配器吗？

**参考答案**：不需要。直接给 `DateUtil` 加一个重载方法，或在新代码里做一次转换即可。
适配器的前提是「被适配的一方不能或不该改」，自己的工具类不满足这个前提。

### 练习 2（解释设计原因）

为什么适配器要「持有」老 SDK，而不是让业务类继承老 SDK？

**参考答案**：继承会把老 SDK 的接口暴露给业务类，业务仍然依赖厂商类型；
而且 Java 单继承，继承 SDK 后不能再继承别的类。持有只暴露业务自己的
`PaymentGateway` 接口，SDK 被关在适配器内部。

### 练习 3（找错误）

有人把折扣计算写进了 `LegacyPayAdapter.pay()`：根据用户等级改金额。
这有什么问题？

**参考答案**：折扣是业务规则，不属于「接口转换」。放进适配器会导致：
换支付渠道时折扣逻辑要重写；适配器越来越难测；同一个规则可能在不同适配器里不一致。
适配器只做「参数/单位/协议」的转换。

## 9. 读完之后

你应该能回答：

1. 适配器为什么存在？——让不兼容的两个接口在不修改双方的前提下合作。
2. 原始实现的问题？——业务直接依赖厂商接口，换算和参数顺序散落各处。
3. 每个角色为什么存在？——目标接口定义业务期望，适配器做转换，被适配者保持不动。
4. 怎么协作？——业务调目标接口 → 适配器转换 → 调用老 SDK。
5. 新场景要不要用？——看两边是否都不能改、接口是否真的不兼容。
