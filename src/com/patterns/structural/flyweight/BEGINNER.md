# 享元模式：通俗入门

> **第一层「入门」材料**：重点是「哪些状态可以共享、哪些必须每个对象自己存」。
> 享元的工程版、缓存淘汰、线程安全与 JDK 中的例子见 [README.md](README.md)。
>
> 可运行代码：[beginner/BeginnerDemo.java](beginner/BeginnerDemo.java)

---

## 1. 一句话说人话

**享元就是：把大量对象里「重复且不变」的那部分抽出来共享，
每个对象只保留自己独有的那一小部分。**

### 什么需求会让开发者想到它

一个文本编辑器一屏要渲染 10000 个字符。每个字符需要：

- 字体、字号、颜色（大量重复，可能只有 3 种组合）；
- 字符本身、屏幕坐标（每个字符都不同）。

第一版给每个字符都 `new` 一份样式对象。10000 个字符 = 10000 个样式对象，
其中只有 3 种内容不同，其余全是重复的字体/字号/颜色。

这不是「对象太多」这么笼统，而是：**可共享的不可变数据，被每个对象各存了一份。**

## 2. 先看不使用享元的代码

完整版在 [BeginnerDemo.java](beginner/BeginnerDemo.java) 的 `before()`：

```java
class OldStyle {
    final String font;
    final int fontSize;
    final String color;
}

class OldGlyph {
    final char ch;
    final OldStyle style;   // 每个字符一份
    final int x;
    final int y;
}
```

循环创建：

```java
OldStyle style = createStyle(i % 3);   // 每次都 new
glyphs.add(new OldGlyph(ch, style, x, y));
```

真实输出：

```text
  字符数：10000
  样式对象数：10000
  合计对象数：20000
  第 1 个和第 4 个字符的样式是同一个对象吗？false
```

---

## 3. 为什么原来的设计不方便

### 3.1 谁依赖谁

```text
Glyph 1 ──▶ Style 1（宋体 12 黑）
Glyph 2 ──▶ Style 2（宋体 12 黑，内容相同但是新对象）
Glyph 3 ──▶ Style 3（宋体 12 黑，内容相同但是新对象）
...
```

对象之间没有共享，重复数据随字符数量线性增长。

### 3.2 问题出在哪

样式是**不可变**的（字体、字号、颜色不会因为某个字符而改变），
本来可以被成千上万个字符共用；但代码在每个字符创建时都 new 了一份。

### 3.3 直接加缓存行不行

可以，但缓存要解决三个问题：

1. **按什么 key 共享**？（字体 + 字号 + 颜色）
2. **共享的对象必须不可变**，否则一个字符改样式会影响所有字符；
3. **缓存的生命周期**由谁管理？

这正是享元模式要明确的三件事，而不只是「加一个 Map」。

---

## 4. 从问题推导出设计

### 第 1 步：区分「内在状态」和「外在状态」

- **内在状态**：可以共享、不随使用场景变化 → 字体、字号、颜色；
- **外在状态**：每个对象独有、由使用方传入 → 字符、坐标。

```java
class TextStyle {          // 内在状态，共享
    private final String font;
    private final int fontSize;
    private final String color;
}

class Glyph {              // 外在状态 + 共享样式的引用
    private final char ch;
    private final TextStyle style;
    private final int x;
    private final int y;
}
```

**为什么必须拆开？** 不拆的话，样式和字符绑在一起，无法单独共享。
**不拆会怎样？** 每个字符继续各存一份样式。

### 第 2 步：让共享对象不可变

```java
private final String font;
private final int fontSize;
private final String color;
```

**为什么？** 共享意味着多个字符引用同一个对象；只要有一个字符能改它，
其他字符的样式就跟着变。**不加会怎样？** 共享变成互相污染。

### 第 3 步：用工厂按 key 缓存

```java
static TextStyle get(int kind) {
    String key = font + "|" + size + "|" + color;
    TextStyle style = CACHE.get(key);
    if (style == null) {
        style = new TextStyle(font, size, color);
        CACHE.put(key, style);
    }
    return style;
}
```

**为什么需要工厂？** 让「相同 key 返回同一个对象」这件事只发生在一处，
调用方不需要自己查 Map。**不加会怎样？** 缓存逻辑散落，容易创建出重复对象。

### 第 4 步：字符只持有引用

```java
TextStyle style = StyleFactory.get(i % 3);
glyphs.add(new Glyph(ch, style, x, y));
```

最终关系：

```text
Glyph 1 ─┐
Glyph 2 ─┼──▶ 同一个 TextStyle（宋体 12 黑）
Glyph 3 ─┘
Glyph 4 ────▶ 另一个 TextStyle（宋体 14 红）
```

真实输出（节选）：

```text
  字符数：10000
  样式对象数：3
  合计对象数：10003
  第 1 个和第 4 个字符的样式是同一个对象吗？true
```

---

## 5. 用执行过程理解代码

前四个字符（样式 kind 依次为 0、1、2、0）：

1. 第 1 个字符：`get(0)` 查缓存，没有 → 创建样式 A，放入缓存；
2. 第 2 个字符：`get(1)` → 创建样式 B；
3. 第 3 个字符：`get(2)` → 创建样式 C；
4. 第 4 个字符：`get(0)` → 命中缓存，返回样式 A；
5. 所以第 1 个和第 4 个字符的 `style` 是同一个引用。

**最容易写错的地方**：

```java
String key = font + "|" + size + "|" + color;
```

key 必须能唯一标识一组内在状态。用 `|` 分隔是为了避免
`("ab", 1)` 和 `("a", 11)` 这类拼接歧义；更严谨的做法是用一个不可变值对象做 key。

## 6. 改造前后对比

### 6.1 字符数从 1 万涨到 10 万

| | 改造前 | 改造后 |
|---|---|---|
| 样式对象 | 10 万 | 仍然是 3 |
| 总对象数 | 20 万 | 10 万 + 3 |
| 改一种字体 | 遍历所有字符 | 改共享样式（但通常应新建样式，而不是改共享对象） |
| 内存 | 随字符数线性增长（含重复样式） | 只随字符数增长（样式固定） |

### 6.2 代价

- 样式必须不可变，设计约束更强；
- 多了一个工厂和 Map 查找，字符很少时反而更慢；
- 缓存要管理生命周期，长期不用的样式需要清理策略；
- 把对象拆成「内在 + 外在」会增加调用方传参的负担。

### 6.3 什么时候不需要

- 对象数量很少（几百个），重复也不明显；
- 对象没有可共享的不可变部分；
- 共享带来的查询成本超过内存收益；
- 还没测量内存占用，就提前优化——享元是典型的「先测量再使用」。

---

## 7. 适用边界

### 适合

- 大量细粒度对象，且大部分状态可以共享；
- 共享状态不可变，外在状态可以由调用方传入；
- 内存是实际瓶颈（文本渲染、地图瓦片、游戏粒子、图标缓存）。

### 不适合

- 对象少、重复少；
- 共享状态需要频繁修改；
- 缓存 key 计算/查找成本高于收益；
- 为了「设计模式」而共享，没有实际内存压力。

### 容易混淆

| 模式 | 区别 |
|---|---|
| **单例** | 单例是「全局只有一个」；享元是「相同 key 共享一个」，可以有多个不同享元 |
| **对象池** | 池里的对象会被借出、修改、归还；享元对象不可变，强调共享而不是复用 |
| **缓存** | 缓存的目的通常是加速访问；享元的目的通常是减少重复对象的内存 |
| **原型** | 原型复制出新对象；享元让多个使用者共享同一个对象 |

> 享元的关键不是「有个 Map」，而是**内在状态可共享且不可变、外在状态外传**。
> 只加缓存但对象仍可变，不叫享元。

## 8. 小练习

### 练习 1（场景判断）

一个系统里只有 50 个 `User` 对象，每个对象有一个 `Role` 字段，
`Role` 只有 3 种且不可变。需要享元吗？

**参考答案**：不需要。50 个对象的重复量太小，引入工厂和缓存反而增加复杂度。
如果 User 数量到百万级、Role 组合很多，才值得考虑。

### 练习 2（解释设计原因）

为什么 `TextStyle` 的字段必须是 `final`，不能提供 setter？

**参考答案**：享元对象会被多个字符共享。如果允许修改，一个字符改字号，
所有共享同一 `TextStyle` 的字符都会跟着变，产生难以排查的串改。
不可变是共享安全的前提。

### 练习 3（找错误）

有人把字符坐标 `x`、`y` 也放进了 `TextStyle`，然后按样式缓存。
会发生什么？

**参考答案**：每个字符的坐标不同，`x/y` 一旦进入 key，缓存几乎无法命中，
每个字符还是会创建新样式，享元失效。坐标属于外在状态，应该留在 `Glyph` 里。

## 9. 读完之后

你应该能回答：

1. 享元为什么存在？——共享大量对象中重复且不可变的部分，降低内存占用。
2. 原始实现的问题？——每个字符一份样式，重复数据随数量线性增长。
3. 每个角色为什么存在？——享元保存内在状态，工厂按 key 保证共享，使用方保存外在状态。
4. 怎么协作？——使用方把外在状态传给享元 → 工厂查缓存/创建 → 多个使用方共享同一对象。
5. 新场景要不要用？——看重复量、共享状态是否不可变、内存是否真的是瓶颈。
