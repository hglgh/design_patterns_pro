# 外观模式：通俗入门

> **第一层「入门」材料**：重点是「谁知道子系统、谁知道顺序」这件事该由谁承担。
> 外观与中介者、适配器的工程对比见 [README.md](README.md)。
>
> 可运行代码：[beginner/BeginnerDemo.java](beginner/BeginnerDemo.java)

---

## 1. 一句话说人话

**外观就是：把一串复杂的操作收成一个按钮，调用方按一下就行，
不用知道里面先开哪个、后开哪个、漏了哪个。**

### 什么需求会让开发者想到它

启动一个应用，需要依次操作四个子系统：

```text
CPU 通电 → 内存加载 → 磁盘挂载 → 网络连接
```

第一版让每个应用自己写这四步。订单应用忘了连网络，启动失败；
报表应用顺序写反、又忘了挂磁盘，也启动失败。两个应用都在重复同一套编排。

外观要解决的不是「某个子系统不好用」，而是：**调用方不该被迫知道
「有哪些子系统、按什么顺序、缺一不可」这些装配知识。**

## 2. 先看不使用外观的代码

完整版在 [BeginnerDemo.java](beginner/BeginnerDemo.java) 的 `before()`：

```java
Cpu cpu = new Cpu();
Memory memory = new Memory();
Disk disk = new Disk();
Network network = new Network();

cpu.powerOn();
memory.load();
disk.mount();
// 忘了 network.connect()
System.out.println("启动结果：" + (network.isConnected() ? "成功" : "失败：网络未连接"));
```

真实输出：

```text
  —— 订单应用启动 ——
    [CPU] 通电
    [内存] 加载系统
    [磁盘] 挂载
  启动结果：失败：网络未连接
  —— 报表应用启动 ——
    [网络] 连接
    [CPU] 通电
    [内存] 加载系统
  启动结果：磁盘未挂载，读不到报表数据
```

## 3. 为什么原来的设计不方便

### 3.1 谁依赖谁

```text
OrderApp  ──▶ Cpu / Memory / Disk / Network（四个都认识）
ReportApp ──▶ Cpu / Memory / Disk / Network（同样四个）
```

每个调用方都依赖整个子系统集合，还要自己维护顺序。

### 3.2 问题出在哪

| 新需求 | 改造前要改哪里 | 后果 |
|---|---|---|
| 启动顺序调整 | 所有应用 | 漏改一个就启动失败 |
| 新增一个子系统 | 所有应用 | 每个应用都要加一行 |
| 关机按逆序 | 所有应用 | 顺序容易写错 |
| 启动失败要回滚 | 所有应用 | 几乎没人写对 |

**为什么抽一个工具方法不够？** 静态工具方法也能收口，但它无法持有子系统状态、
无法替换实现、也无法参与依赖注入。外观是一个对象，能管理生命周期和状态。

---

## 4. 从问题推导出设计

### 第 1 步：把子系统收进一个类

```java
class ComputerFacade {
    private final Cpu cpu = new Cpu();
    private final Memory memory = new Memory();
    private final Disk disk = new Disk();
    private final Network network = new Network();
}
```

**为什么由外观持有？** 因为「先开哪个、后开哪个」需要知道当前状态，
这些状态属于这次启动过程。**不加会怎样？** 调用方继续自己 new 四个对象。

### 第 2 步：暴露一个 `start()`

```java
void start() {
    cpu.powerOn();
    memory.load();
    disk.mount();
    network.connect();
}
```

**为什么顺序写在外观里？** 顺序是子系统之间的协作规则，不该复制到每个调用方。
**不加会怎样？** 每个应用继续各自编排，漏步骤无法避免。

### 第 3 步：把逆序也收进来

```java
void shutdown() {
    network.disconnect();
    disk.unmount();
    memory.clear();
    cpu.powerOff();
}
```

**为什么关机也要外观？** 因为「逆序」也是协作知识；只提供 start 不提供 shutdown，
调用方仍要自己推导逆序。

### 第 4 步：客户端只调一个方法

```java
ComputerFacade computer = new ComputerFacade();
computer.start();
```

最终关系：

```text
OrderApp ─┐
          ├──▶ ComputerFacade ──▶ Cpu / Memory / Disk / Network
ReportApp ┘        （唯一知道顺序的人）
```

真实输出（节选）：

```text
  —— 订单应用启动 ——
    [CPU] 通电
    [内存] 加载系统
    [磁盘] 挂载
    [网络] 连接
  启动结果：成功
  —— 关机 ——
    [网络] 断开
    [磁盘] 卸载
    [内存] 清空
    [CPU] 断电
```

## 5. 用执行过程理解代码

`computer.start()`：

1. 进入 `ComputerFacade.start()`；
2. 依次调用 `cpu.powerOn()`、`memory.load()`、`disk.mount()`、`network.connect()`；
3. 每个子系统只做自己的事，不知道外观的存在；
4. 返回后，调用方拿到的是一台「已启动」的电脑。

**最容易忽略的点**：外观没有把子系统「藏起来」，它只是提供了一个简单入口。
高级用户仍然可以直接 `new Cpu().powerOn()`。外观是**便利层**，不是访问控制层。

---

## 6. 改造前后对比

### 6.1 新增一个子系统（例如 GPU）

| | 改造前 | 改造后 |
|---|---|---|
| 修改应用 | 每个应用加一行 | 0 |
| 修改外观 | — | `start()` 里加一行 |
| 顺序知识 | 散落在各应用 | 只在外观里 |
| 漏步骤风险 | 高 | 低（集中一处） |

### 6.2 代价

- 外观会逐渐变成「什么都知道」的大类，容易继续塞业务规则；
- 多一层调用，简单场景显得绕；
- 子系统行为变化时，外观可能需要跟着改；
- 外观不阻止别人绕过它，团队仍可能直接调子系统。

### 6.3 什么时候不需要

- 只有一个调用方，且只调用一次；
- 子系统只有一个/两个，顺序无所谓；
- 已经有框架/容器负责装配和生命周期。

---

## 7. 适用边界

### 适合

- 多个子系统需要按固定顺序协作，调用方不该知道细节；
- 要给遗留系统提供一个清晰的入口；
- 需要把「启动/关闭/回滚」这类生命周期收口；
- 分层架构中，为上层提供一个稳定的服务入口。

### 不适合

- 子系统简单、调用点很少；
- 外观开始承载业务规则，变成上帝类；
- 需要的是「对象之间双向通信」——那是中介者；
- 需要的是「接口转换」——那是适配器。

### 容易混淆

| 模式 | 区别 |
|---|---|
| **中介者** | 中介者让同事之间**通过它双向通信**，同事知道中介；外观是**单向**简化，子系统不知道外观 |
| **适配器** | 适配器转换一个接口；外观简化多个子系统的使用 |
| **单例** | 外观可以是单例，但「唯一」不是外观的目的；外观的目的是简化入口 |
| **门面 vs 分层** | 外观是代码结构，分层是架构原则；外观常用来实现层间边界 |

## 8. 小练习

### 练习 1（场景判断）

一个 `EmailSender` 只有 `send()` 一个方法，调用方也只有一处。
需要再包一个 `EmailFacade` 吗？

**参考答案**：不需要。只有一个子系统、一个方法、一个调用点，外观没有简化任何东西，
只是多了一层。外观的价值来自「多个子系统 + 固定顺序 + 多个调用方」。

### 练习 2（解释设计原因）

为什么 `shutdown()` 要放在外观里，而不是让调用方自己按逆序调用？

**参考答案**：逆序也是子系统之间的协作规则，和启动顺序一样属于「装配知识」。
放在外观里，规则只有一份；放在调用方，每个应用都要自己推导，容易写错。

### 练习 3（边界判断）

团队把折扣计算、库存扣减也写进了 `ComputerFacade`，说「反正都收在一起了」。
这样对吗？

**参考答案**：不对。外观的职责是**简化子系统调用**，不是承载业务规则。
业务规则进来后，外观会变成上帝类，难以测试和复用。业务规则应该放在领域服务里，
外观只负责编排。

## 9. 读完之后

你应该能回答：

1. 外观为什么存在？——把多个子系统的协作顺序收口成一个简单入口。
2. 原始实现的问题？——每个调用方重复编排、漏步骤、顺序写错。
3. 每个角色为什么存在？——外观持有子系统并编排，子系统只做自己的事。
4. 怎么协作？——客户端调 `start()` → 外观按顺序调子系统 → 返回结果。
5. 新场景要不要用？——看是否存在多个子系统、固定顺序、多个调用方。
