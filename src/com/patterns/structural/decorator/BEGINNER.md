# 装饰器模式：通俗入门

> **第一层「入门」材料**：重点是「不通过继承，怎么在运行时给对象叠加功能」。
> 装饰器的工程版、透明/半透明装饰、与代理的深入对比见 [README.md](README.md)。
>
> 可运行代码：[beginner/BeginnerDemo.java](beginner/BeginnerDemo.java)

---

## 1. 一句话说人话

**装饰器就是：给一个对象套一层「壳」，壳和原对象长得一样，
但多做一点事，而且可以一层层套下去。**

### 什么需求会让开发者想到它

咖啡店卖浓缩，可以加奶、加糖、加燕麦奶。第一版用继承：

```text
Espresso、MilkEspresso、SugarEspresso、MilkSugarEspresso……
```

3 种加料 = 8 个组合类；4 种 = 16 个。更麻烦的是：

- 想「加两份奶」？没有 `MilkMilkEspresso`；
- 想根据用户选择在运行时决定加什么？继承在编译期就定死了；
- 想调整价格？每个组合类里都写了一遍。

装饰器要解决的是：**功能组合在运行时才确定，而且组合数量会爆炸。**

## 2. 先看不使用装饰器的代码

完整版在 [BeginnerDemo.java](beginner/BeginnerDemo.java) 的 `before()`：

```java
abstract class OldCoffee {
    abstract int cost();
    abstract String describe();
}

class OldEspresso extends OldCoffee { ... }
class OldMilkEspresso extends OldCoffee { ... }
class OldSugarEspresso extends OldCoffee { ... }
class OldMilkSugarEspresso extends OldCoffee { ... }
```

真实输出：

```text
  浓缩（10 元）
  浓缩+奶（12 元）
  浓缩+糖（11 元）
  浓缩+奶+糖（13 元）
```

---

## 3. 为什么原来的设计不方便

### 3.1 谁依赖谁

```text
OldCoffee
  ├── OldEspresso
  ├── OldMilkEspresso
  ├── OldSugarEspresso
  └── OldMilkSugarEspresso
```

每个子类都同时包含「咖啡种类」和「加料组合」两个决定。
加料一多，子类数量按组合数增长。

### 3.2 新增需求会怎样

| 新需求 | 改造前 | 结果 |
|---|---|---|
| 加燕麦奶 | 新增 4 个组合类（纯、奶、糖、奶糖各配燕麦） | 类爆炸 |
| 加两份奶 | 新增 `MilkMilkEspresso` | 组合无法穷举 |
| 运行时按用户选择加料 | 做不到 | 继承是编译期绑定 |
| 修改奶的价格 | 所有含奶的子类 | 改多处，易漏 |

**为什么加个 `if (milk)` 不够？** 那会让一个咖啡类知道所有加料、
价格和描述逻辑堆在一起；加一种料就要改这个类，而且无法复用「加奶」这段行为。

## 4. 从问题推导出设计

### 第 1 步：保留一个「咖啡」接口

```java
interface Coffee {
    int cost();
    String describe();
}
```

**为什么？** 装饰器和被装饰者必须长得一样，客户端才能一视同仁。
**不加会怎样？** 装饰器无法替换原对象，客户端要区分「加料前/加料后」。

### 第 2 步：写一个装饰者基类，持有同一个接口

```java
abstract class CoffeeDecorator implements Coffee {
    protected final Coffee inner;

    CoffeeDecorator(Coffee inner) {
        this.inner = inner;
    }
}
```

**为什么既实现又持有？** 实现是为了「长得一样」，持有是为了「调用内层」。
这两件事同时存在，才是装饰器。
**不加会怎样？** 要么无法替换，要么无法叠加。

### 第 3 步：每个加料一个装饰器

```java
class Milk extends CoffeeDecorator {
    public int cost() { return inner.cost() + 2; }
    public String describe() { return inner.describe() + " + 奶"; }
}
```

**为什么加料自己算价格？** 每个装饰器只负责自己那一份增量，
价格由套娃逐层累加，不需要一个「总价表」。

### 第 4 步：运行时套

```java
Coffee coffee = new Sugar(new Milk(new Espresso()));
```

**为什么这样能工作？** 最内层是 `Espresso`，`Milk` 包住它，`Sugar` 再包住 `Milk`；
调用 `cost()` 时，每层先问内层，再加自己的增量。

最终关系：

```text
Sugar ──持有──▶ Milk ──持有──▶ Espresso
  cost() = 内层 + 1      cost() = 内层 + 2      cost() = 10
```

真实输出（节选）：

```text
  浓缩（10 元）
  浓缩 + 奶（12 元）
  浓缩 + 奶 + 糖（13 元）
  浓缩 + 奶 + 奶（14 元）
  —— 新增燕麦奶：只加一个装饰器类，已有类都不改 ——
  浓缩 + 燕麦奶 + 糖（14 元）
```

## 5. 用执行过程理解代码

`new Sugar(new Milk(new Espresso()))`：

1. 创建 `Espresso`（cost=10）；
2. 创建 `Milk`，`inner` 指向 Espresso；
3. 创建 `Sugar`，`inner` 指向 Milk；
4. `cost()` 调 Sugar → `inner.cost()` 调 Milk → `inner.cost()` 调 Espresso；
5. 返回 10 → Milk 加 2 → Sugar 加 1 → 13。

**最容易混淆的地方**：

```java
return inner.cost() + 2;
```

不是 `cost() + 2`（会无限递归），而是**先问内层**。装饰器把「自己这部分」
和「内层那部分」分开，才能任意叠加。

## 6. 改造前后对比

### 6.1 新增燕麦奶

| | 改造前 | 改造后 |
|---|---|---|
| 新增类 | 4 个组合子类 | 1 个 `OatMilk` |
| 修改已有类 | 0（但组合类继续膨胀） | 0 |
| 加两份奶 | 需要新类 | `new Milk(new Milk(...))` |
| 运行时选择 | 做不到 | 按用户选择套 |
| 价格计算 | 每个组合类写死 | 各装饰器只加自己的增量 |

### 6.2 代价

- 每加一种功能多一个小类；
- 层数多了，调试要逐层点进去；
- 装饰顺序会影响结果（描述顺序、某些前后处理）；
- 如果组合固定且很少，直接写几个类更直观。

### 6.3 什么时候不需要

- 功能组合只有一两种，写死更清楚；
- 需要的是「改变接口」——那是适配器；
- 需要的是「控制访问」——那是代理；
- 需要的是「树形整体/部分」——那是组合。

---

## 7. 适用边界

### 适合

- 需要在不改原类的前提下，运行时叠加功能；
- 功能可以独立组合，组合数量会增长；
- 想避免继承导致的组合爆炸；
- 需要给一批对象统一加横切功能（日志、缓存、压缩、加密）。

### 不适合

- 功能固定、组合很少；
- 装饰器需要访问被装饰者的内部细节（说明抽象没设计好）；
- 对象创建成本很低，直接 new 一个带参数的实现更简单。

### 容易混淆

| 模式 | 目的 | 与装饰器的区别 |
|---|---|---|
| **代理** | 控制访问（鉴权、延迟加载、远程） | 代理通常自己创建目标，强调「能不能访问」；装饰器接收现成对象，强调「叠加功能」 |
| **适配器** | 转换接口 | 适配器改变接口；装饰器保持接口不变 |
| **组合** | 树形整体/部分 | 组合持有多个子节点；装饰器只持有一个内层 |
| **继承** | 编译期扩展 | 继承在编译期定死，装饰器在运行时叠加 |

> 装饰器和代理在代码结构上几乎一样（同接口 + 持有），区别在**意图**：
> 装饰器是「加功能」，代理是「控访问」。意图不同，边界和失败处理也不同。

## 8. 小练习

### 练习 1（场景判断）

一个系统只有「普通用户」和「VIP 用户」两种价格，VIP 永远九折，
未来也不会加别的折扣。需要装饰器吗？

**参考答案**：不需要。两种固定价格用一个策略或直接一个 if 就够。
装饰器适合「功能可任意组合、组合会增长」的场景，两种固定情况是过度设计。

### 练习 2（解释设计原因）

为什么 `Milk` 要实现 `Coffee` 接口，同时还要持有 `Coffee`？

**参考答案**：实现接口是为了能替换原对象，客户端可以把它当普通咖啡用；
持有是为了调用内层，把自己的增量叠加到内层结果上。
只实现不持有，无法叠加；只持有不实现，无法替换。

### 练习 3（找 bug）

有人把 `Milk.cost()` 写成 `return cost() + 2;`，会发生什么？

**参考答案**：无限递归，最终 `StackOverflowError`。应该调用 `inner.cost()`，
先拿到内层的结果，再加自己的增量。

## 9. 读完之后

你应该能回答：

1. 装饰器为什么存在？——运行时给对象叠加功能，避免继承组合爆炸。
2. 原始实现的问题？——每个组合一个子类，无法运行时叠加，价格逻辑重复。
3. 每个角色为什么存在？——组件接口统一类型，装饰者基类持有内层，具体装饰器加自己的增量。
4. 怎么协作？——一层层套，调用时逐层向内委托，结果逐层向外累加。
5. 新场景要不要用？——看功能是否可独立组合、是否需要运行时叠加。
