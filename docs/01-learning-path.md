# 推荐学习顺序：23 种模式该按什么顺序学

> 本文回答三个问题：**先学哪个、后学哪个、每个模式真正卡人的地方在哪里。**
> 目录页见 [README](../README.md)，相似模式对比见 [02-pattern-comparison.md](02-pattern-comparison.md)，组合与继承的原理见 [07-composition-vs-inheritance.md](07-composition-vs-inheritance.md)。

## 0. 先纠正一个常见误区

多数教程按「创建型 → 结构型 → 行为型」平铺直叙，于是很多人学完 23 个名词，遇到真实需求仍然一张口就是 `if/else`。

原因不是记性不好，而是**顺序错了**：GoF 的三分类是「按目的分类」，不是「按理解难度分类」。

真正决定一个模式好不好懂的，是它依赖多少个前置概念。所以本文给的不是分类顺序，而是**依赖顺序**。

### 三个前置概念

学任何模式之前，先把这三件事弄清楚，否则后面全是背名词：

| 概念 | 含义 | 在哪个模式里第一次真正用到 |
|---|---|---|
| **面向接口编程** | 变量声明成接口类型，运行时才决定是哪个实现 | 策略（`PriceCalculator` 持有 `DiscountStrategy`） |
| **[组合优于继承](07-composition-vs-inheritance.md)** | 把行为做成成员对象，而不是做成父类方法 | 装饰器（`TextDecorator` 持有一个 `TextComponent`） |
| **多态分派** | 调 `x.foo()` 时执行哪个 `foo`，由 `x` 的运行时类型决定 | 模板方法（父类调 `hook()`，执行的是子类版本） |

这三个概念在本项目中都有最朴素的例子。**如果你能用自己的话讲清 `TextDecorator` 为什么既 `implements TextComponent` 又持有一个 `TextComponent` 字段**，前置概念就算过关了。

## 1. 三条路线

同一个项目，三种目标，三种走法。**先确定你的目标，别贪多。**

### 路线 A：面试速成（约 20 小时）

目标：能在白板上写出结构、说清适用场景、答出与相似模式的区别。

| 顺序 | 模式 | 入口 | 为什么排这个位置 | 建议投入 |
|---|---|---|---|---|
| 1 | 单例 | [SingletonClient](../src/com/patterns/creational/singleton/SingletonClient.java) | 唯一一个不需要多态的模式，最容易建立信心；同时是面试第一问 | 1.5h |
| 2 | 工厂方法 | [Client](../src/com/patterns/creational/factorymethod/Client.java) | 「把 new 挪走」是所有解耦的起点 | 1.5h |
| 3 | 策略 | [Client](../src/com/patterns/behavioral/strategy/Client.java) | 最典型的「接口 + 实现 + 上下文」三件套，后面所有模式都是它的变形 | 2h |
| 4 | 观察者 | [Client](../src/com/patterns/behavioral/observer/Client.java) | 一对多通知，业务代码里出现频率最高 | 2h |
| 5 | 装饰器 | [Client](../src/com/patterns/structural/decorator/Client.java) | 「包装」家族的母版，学会后适配器/代理都省一半力气 | 2h |
| 6 | 代理 | [Client](../src/com/patterns/structural/proxy/Client.java) | 与装饰器同构，重点学动态代理和「包装目的不同」 | 2.5h |
| 7 | 责任链 | [Client](../src/com/patterns/behavioral/chainofresponsibility/Client.java) | 面试高频，且能立刻用掉「持有同类型引用」这个技巧 | 2h |
| 8 | 模板方法 | [Client](../src/com/patterns/behavioral/templatemethod/Client.java) | 继承路线的最后代表，理解「骨架 + 钩子」 | 1.5h |
| 9 | 适配器 | [Client](../src/com/patterns/structural/adapter/Client.java) | 与装饰器/代理构成三兄弟对比，一起记最省力 | 1.5h |
| 10 | 建造者 | [Client](../src/com/patterns/creational/builder/Client.java) | 参数多的对象怎么造，链式调用怎么写 | 1.5h |

**速成路线的取舍**：跳过组合、桥接、享元、中介者、备忘录、迭代器、解释器、访问者。这些不是不重要，而是面试出现频率低、且不理解也不影响你写业务代码。等真遇到场景再回来。

### 路线 B：系统学习（约 60 小时）

目标：完整掌握 23 种模式，能独立判断「这个需求该不该用模式」。

分五段，每段之间有硬性前置关系：

**第 1 段：解耦「创建」（8h）**

```
单例 → 工厂方法 → 抽象工厂 → 建造者 → 原型
```

这一段的核心问题只有一个：**对象创建这件事，为什么要从使用方挪走？**

五种模式是五种挪法：

- 单例：干脆不让别人 new
- 工厂方法：把 new 交给子类
- 抽象工厂：把「一族对象的 new」打包交给一个工厂
- 建造者：把「一个复杂对象的多次 new + set」拆成步骤
- 原型：不 new，直接复制现成的

**第 2 段：解耦「结构」（14h）**

```
适配器 → 装饰器 → 代理 → 外观 → 组合 → 桥接 → 享元
```

这一段的核心问题：**两个类怎么组合，才能既不互相绑死、又能拼出新能力？**

注意顺序：前四个是「一对一包装/门面」，后三个才涉及「多对多/树形/共享」。**不要按字母或分类顺序学享元**，享元需要你先理解「对象数量」这件事为什么重要。

**第 3 段：解耦「算法」（12h）**

```
策略 → 模板方法 → 命令 → 责任链 → 状态
```

这一段的核心问题：**一段会变的逻辑，应该放在哪里？**

这五个模式是同一个问题的五种答案，而且它们经常被混用。学完这一段，你应该能回答：

- 为什么 `switch` 分支增多时，第一反应是策略而不是责任链？
- 为什么状态模式需要「状态知道自己下一个是谁」，策略模式不需要？
- 命令模式比策略模式多出来的那个「对象」，到底多在哪？

**第 4 段：解耦「协作与遍历」（16h）**

```
观察者 → 中介者 → 迭代器 → 备忘录
```

这一段的核心问题：**多个对象之间怎么通信、怎么访问、怎么回滚？**

观察者要放在中介者前面：观察者是「一对多广播」，中介者是「多对多转接」，后者是前者的复杂化。

迭代器独立性强，可以插在任何位置。备忘录要放最后，因为它涉及「谁来保管状态」这个设计判断，初学者容易写成「什么都存」。

**第 5 段：解耦「操作与文法」（10h）**

```
访问者 → 解释器 → 组合应用
```

访问者放最后，因为它是 23 个里**唯一需要「双分派」**的模式，没有前面的多态基础根本讲不通。

解释器更难：它要求你能把「规则」翻译成「类结构」。**如果时间紧，解释器可以只读到能写出加减乘除求值器即可。**

最后用 [组合应用](../src/com/patterns/combined/orderservice/README.md) 收尾。它的价值不在「又学了一个模式」，而在让你看到**四个模式在同一个需求里各自负责哪一块、边界在哪里**。

### 路线 C：深挖原理（不设上限）

目标：能回答「为什么这样设计，换一种写法会怎样」。

走法：挑一个模式，读完 README 的 §1 到 §9 后，**先不看 §7（扩展对比），自己写一段扩展代码，再对照**。

本项目的 24 份 README 里，§7 都是「新需求来了改哪里」的实测推演，§8 都是「常见误区」，§9 都是面试题。这三节最适合做自测。

## 2. 每个模式真正的卡点

下面是**光看定义绝对看不懂、必须看代码才能过的那一句话**。按学习顺序排列。

### 创建型

| 模式 | 卡点 | 卡在哪 |
|---|---|---|
| 单例 | 「双重检查为什么要加 `volatile`」 | 不加会因指令重排拿到**半初始化对象**。`DoubleCheckLockSingleton` 里那一行 `volatile` 不是可选优化，是正确性要求 |
| 单例 | 「枚举单例为什么防得住反射」 | 不是语法糖。JVM 层面禁止对 enum 做反射构造，且反序列化返回同一实例 |
| 工厂方法 | 「工厂方法 vs 简单工厂」 | 简单工厂一个类里 `switch`，新增产品要改工厂；工厂方法每个产品一个工厂类，新增产品只加类 |
| 抽象工厂 | 「产品族 vs 产品等级」 | 这两个词看定义永远不懂。看 `UIFactory` 里 `Button` + `TextBox` 必须是同一平台，就懂了 |
| 建造者 | 「`Director` 到底要不要」 | 不要也能用（`Client` 里链式调用直接 `build()`）；要它是为了复用「组装顺序」 |
| 原型 | 「浅拷贝为什么是坑」 | 克隆后两个对象共享同一个引用类型字段，改一个另一个跟着变 |

### 结构型

| 模式 | 卡点 | 卡在哪 |
|---|---|---|
| 适配器 | 「适配器和装饰器都在包装，区别在哪」 | **被包对象的接口是否保留**。装饰器保留（同接口），适配器改变（转成另一个接口） |
| 装饰器 | 「为什么装饰器必须和被装饰者同接口」 | 不同接口就没法再套第二层，也就没法任意叠加 |
| 装饰器 | 「顺序为什么影响结果」 | `Bold(Color(text))` 和 `Color(Bold(text))` 在纯文本下输出相同，但如果装饰器带状态或副作用（如组合示例的封顶与日志），顺序就改变语义 |
| 代理 | 「静态代理和动态代理的分界线」 | 静态代理一个类代理一个目标；动态代理一个 `InvocationHandler` 代理任意目标。看 `DynamicImageProxy` 就明白 |
| 外观 | 「外观是不是就是又包了一层」 | 外观**不新增能力**，只把 N 个子系统的调用顺序固化下来。判断标准：去掉外观，功能还在，只是调用方变复杂 |
| 组合 | 「叶子节点的 `add` 怎么办」 | 透明式（叶子也实现 `add` 并抛异常）vs 安全式（接口里不定义 `add`，只在 `Directory` 上加）。本项目 `FileSystemNode` 采用**安全式**，代价是编译期拿不到统一的 `add` |
| 桥接 | 「什么叫两个维度独立变化」 | 不是「两个类」。是两个轴：`Message`（普通/定时/紧急）× `MessageSender`（邮件/短信/微信/钉钉），任意组合不产生类爆炸 |
| 享元 | 「内部状态 vs 外部状态怎么分」 | 内部分享（`Glyph` 的字符与字体），外部传入（`CharacterView` 的位置与颜色）。判断标准：这个字段会不会因使用场景而不同 |

### 行为型

| 模式 | 卡点 | 卡在哪 |
|---|---|---|
| 策略 | 「策略之间需不需要知道彼此」 | 不需要。一旦需要，「选哪个策略」就该由工厂或调用方决定，而不是策略自己 |
| 策略 | 「策略 vs 简单 if/else」 | 分支少（≤3）且稳定时，if/else 更好读。策略的收益在「可独立测试 + 可运行时替换」 |
| 模板方法 | 「抽象方法 vs 钩子方法」 | 抽象方法子类**必须**实现；钩子方法有默认实现，子类**可以**选择性覆盖。看 `OrderProcessTemplate` 里哪几个是钩子 |
| 模板方法 | 「为什么 `process()` 要声明成 `final`」 | 不 final 子类就能改掉骨架，模板方法就失效了 |
| 命令 | 「`undo` 到底怎么实现」 | 三层：逆操作（`UpdateConfigCommand` 记旧值）、快照（整对象存一份）、事务（数据库回滚）。选哪层看代价 |
| 命令 | 「宏命令失败后的补偿为什么必须倒序」 | `MacroCommand.rollback()` 用 `listIterator(size())` 逆序遍历。正序执行 A→B→C，补偿必须 C→B→A，否则中间态错误。注意它叫 rollback 不叫 undo——宏命令本身**不实现** `UndoableCommand`，因为不是每一步都能撤销 |
| 责任链 | 「没人处理怎么办」 | 三种设计：静默丢弃、抛异常、兜底节点。本项目用第四种：兜底放在**链对象**的 `submit()` 里，而不是在链尾挂一个节点——因为「没人处理」是链的语义补全，不是某个节点的业务 |
| 责任链 | 「顺序错了会怎样」 | 责任链的语义完全依赖顺序。折扣链里满减在折扣前还是后，结果不同 |
| 状态 | 「状态转移由谁驱动」 | 三种：状态自己 `next()`、上下文判断、外部转移表（`TransitionTable`）。本项目用第三种，好处是转移关系一眼看全 |
| 观察者 | 「通知过程中增删观察者会怎样」 | 边遍历边改集合会 `ConcurrentModificationException`。必须先拷贝快照 |
| 观察者 | 「一个观察者抛异常，其他还通知吗」 | 这是设计决定，不是语法问题。本项目 `ContentCreator` 的做法看代码 |
| 迭代器 | 「遍历算法为什么不算聚合类的职责」 | 放聚合类里，每加一种遍历方式就要改聚合类；放迭代器里，聚合类永不变 |
| 迭代器 | 「为什么不能在遍历中修改集合」 | 不是 Java 故意刁难，是「遍历位置」这个状态会失效。`FilteringIterator` 展示了过滤迭代器怎么处理 |
| 中介者 | 「中介者会不会变成上帝对象」 | 会。`CollaborationHub` 就是一次集中，代价是所有交互逻辑都挤在一个类里。判断标准：消息类型多到什么程度就该拆分 |
| 备忘录 | 「备忘录由谁保管」 | 三种：发起人自己（简单但职责不清）、管理者 `SnapshotHistory`（本项目）、外部存储（可持久化） |
| 备忘录 | 「为什么要有条数上限」 | `EditorLimits` 不是过度设计。无上限的 `SnapshotHistory` 在长会话里必然 OOM |
| 访问者 | 「什么叫双分派」 | `element.accept(visitor)` 第一次分派选元素类型，`visitor.visitXxx(this)` 第二次分派选访问者。**两层都看运行时类型** |
| 访问者 | 「为什么加新元素难、加新操作易」 | 加操作 = 加一个访问者类；加元素 = 改 `DocumentVisitor` 接口 + 所有实现。这是它的固有代价，不是实现问题 |
| 解释器 | 「类结构为什么由文法决定」 | 文法里每个规则对应一个 `Expression` 实现。文法复杂 → 类爆炸。所以解释器只适合小语言 |

## 3. 三步学习法

每一份模式 README 都按同一结构写，建议配套使用：

**第一步：只看 §1 和 §2（不看答案）**

- 读 §1 的现实案例，问自己：如果让我写，我会怎么写？
- 读 §2 的原始实现（那是刻意写坏的版本），找出你觉得别扭的地方

**第二步：读 §3 和 §4，验证你的判断**

- §3 讲设计动机，包括「什么时候不需要这个模式」
- §4 讲设计推导，是「从坏代码一步步改成好代码」的过程

如果 §4 的每一步你都能提前想到，说明这个模式你已经掌握了。

**第三步：读 §5 到 §9**

- §5 逐文件讲代码，重点看「这个类为什么必须存在」
- §6 是真实运行输出，可以自己跑一遍对照
- §7 是扩展推演，最适合做练习
- §8 是误区，**这一节的价值往往高于前面所有节**
- §9 是面试题，可以当作自测

## 4. 达标标准

不要用「看完了」作为完成标志。用下面三条：

| 层级 | 标准 | 检验方式 |
|---|---|---|
| 看懂 | 能说出这个模式解决什么问题 | 用一句话讲给不写代码的人听 |
| 会写 | 能不看资料写出最小可运行版本 | 关掉 README，只留 IDE |
| 会判断 | 能说出「这个需求不该用这个模式」的理由 | 读 §8 的误区，逐条判断自己是否踩过 |

**只有第三层才算真正学会。** 本项目 24 份 README 的 §8 都写了「什么时候不该用」，就是为了这一层。

## 5. 常见走偏

| 走偏 | 表现 | 纠正 |
|---|---|---|
| 背结构 | 能画类图，写不出代码 | 每个模式至少手写一次最小实现 |
| 套模式 | 一个 `if` 也要抽成策略 | 分支 ≤3 且稳定时，直接写 `if` |
| 过度抽象 | 三个类能解决的拆成八个 | 本项目组合示例里 `LegacyOrderService` 只用 210 行（含注释）就能覆盖基础需求 |
| 只学不用 | 学完 23 个，业务里一个没用上 | 从「重复的 `if/else`」「会变的通知方式」「多步构造」这三类代码入手 |
| 混淆相似模式 | 张口就是「策略和责任链差不多」 | 读 [02-pattern-comparison.md](02-pattern-comparison.md)，重点看「区别用一句话怎么说」 |

## 6. 一页速查

```
只想面试      → 单例 工厂方法 策略 观察者 装饰器 代理 责任链 模板方法 适配器 建造者
想系统掌握    → 创建(8h) → 结构(14h) → 算法(12h) → 协作(16h) → 操作(10h)
想深挖        → 任选一个，读完 §1-§6 后自己写 §7 的扩展，再对照
```

各模块的实际规模（源文件数 / 代码行数 / 文档行数）见 [05-verification.md](05-verification.md)。
