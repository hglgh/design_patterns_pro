# 入门层教学模板：从「为什么」讲到「什么时候不用」

> 本文是整个项目**第一层（通俗入门）**的写作规范，也是 23 份 `BEGINNER.md` 的验收尺子。
> 第二层（深度学习）仍是各模式目录下的 `README.md`，不要求初学者一上来就读。
>
> 模板来自命令模式试点的实际写作经验，不是凭空设计的目录。

---

## 0. 两层材料怎么分工

| | 第一层 `BEGINNER.md` | 第二层 `README.md` |
|---|---|---|
| 读者 | 学过 Java 语法，没系统学过设计模式 | 已理解设计动机，要做工程实现/面试 |
| 目标 | 能判断「为什么用、什么时候不用」 | 能写对、能扩展、能回答细节追问 |
| 代码 | 一个文件、可运行、少抽象 | 完整包结构、异常体系、边界处理 |
| 篇幅 | 1500～3000 字，只讲一个核心矛盾 | 不限，允许深入 |
| 角色 | 先讲问题，角色是推导出来的 | 可以系统讲解角色、类图、协作 |
| 链接 | 结尾指向深度文档 | 顶部回链入门文档 |

**硬规则**：入门文档不得要求读者先理解第二层的任何概念；深度文档不得删除已有的有效内容。

## 1. 八段式结构

每一份 `BEGINNER.md` 必须按下面的顺序写。顺序本身就是教学法：
**先有痛点，再有设计；先有最小版本，再有完整结构。**

### ① 一句话说人话 + 一个具体场景

- 第一句用普通人都懂的话说清「它把什么麻烦变成了什么方便」。
- 紧接着给一个**软件开发场景**（不是餐厅比喻），说明什么需求会逼出这个模式。
- 场景里要出现**具体数字/字段/角色**，不要写「某系统需要扩展」。
- 禁止在这一节列角色表、贴 UML、背 GoF 定义。

### ② 先展示不使用的代码

- 给一段**简短、完整、能运行**的 Java 代码（可指向 `beginner/BeginnerDemo.java` 的对应片段）。
- 代码要能暴露真实问题：新增业务改多处、一个类职责过多、对象依赖成网、创建受限、遍历/操作难统一……
- **不同模式必须暴露不同的痛点**，不能都写成「if-else 太多」。
- 代码之后给出**真实运行结果**，让问题可以被看见。

### ③ 解释为什么原来的设计不方便

必须逐条回答，不能只写「耦合高、违反开闭原则」：

- 谁依赖谁？（画出 3～6 个类的依赖方向）
- 哪段代码导致问题？（引用具体行/方法）
- 新增一个需求会改哪些类？改几处？
- 为什么加一个 if-else 或直接调方法解决不了？

建议用一张「新需求 → 要改哪里 → 代价」的表。

### ④ 从问题推导出设计

- 一步一步加抽象，每一步只解决上一步留下的一个具体问题。
- 每加一个接口/类，回答四问：
  1. 为什么需要它？
  2. 它解决了前面哪个问题？
  3. 不加会有什么后果？
  4. 它和已有的类有什么区别？
- **先给最小可用版本，再补第二个实现/第二个维度**；禁止先甩出完整类图让人背。
- 可以在最后用一张 ASCII 图收束对象关系，但图必须能看出「谁依赖谁、为什么」。

### ⑤ 用具体数据和执行过程讲代码

- 用一组具体输入，按真实执行顺序讲：先创建什么、谁持有谁、调用哪个方法、输出什么。
- 必须解释最容易写错/最容易混淆的 2～3 处代码，说明「这行改变了什么」。
- 不要逐行翻译代码字面意思。
- 输出必须与 `beginner/BeginnerDemo.java` 的实际运行结果一致；可标「节选」，但不得改写。

### ⑥ 对比改造前后

- 用一个**新增需求**验证：改造前改哪些类，改造后改哪些类。
- 必须诚实说明调用方仍需改什么（例如仍要 `submit`、仍要选择策略）。
- 列出引入模式新增的维护成本：类数量、间接层、命名、生命周期、测试影响。
- 如果简单实现已经足够，明确写「这个场景不需要该模式」。

### ⑦ 明确适用边界

- 适合的 3～5 个场景，要具体到「有排队/有审计/有两种独立变化维度」这种可判断的条件。
- 不适合的 2～3 个场景。
- 与 1～3 个易混模式对比：**两者解决的问题有什么不同**，不要只比类图。
- 如果模式常被误解（如命令≠事件、代理≠装饰器），单独点破。

### ⑧ 小练习（2～4 题）

至少包含：

1. 一道**场景判断题**：给一个新业务，问要不要用这个模式，并说明理由；
2. 一道**解释设计原因**题：问某个类/接口为什么必须存在，去掉会怎样。

可以再加一道执行过程题或扩展推导题。答案必须给**推导过程**，不能只给结论；
最后附「读完后应能回答的 5 个问题」，对应项目验收标准。

## 2. 入门代码约定

| 约定 | 原因 |
|---|---|
| 放在 `<pattern>/beginner/BeginnerDemo.java` | 与工程版隔离，避免类名冲突 |
| 一个文件装下「改造前 + 改造后」 | 读者只需编译运行一次，就能对照 |
| 只用 `class` / `interface` / `List` / `Map` 等基础语法 | 入门层不引入 record、sealed、注解、框架 |
| `main` 先跑改造前，再跑改造后 | 让问题先发生，再给解法 |
| 输出包含「问题清单 / 代价」 | 代码本身也要能讲清边界 |
| 不抛自定义异常体系 | 业务失败用返回值或 JDK 异常表示，并在文档中说明这是简化 |
| 变量名用业务词，不用 `A/B/Foo` | 读者应能只看名字理解场景 |
| 输出确定、无时间/随机数/哈希码 | 文档才能逐字引用，读者才能复现 |

运行方式（在项目根目录）：

```bash
javac --release 25 -encoding UTF-8 -d out src/com/patterns/<分类>/<模式>/beginner/BeginnerDemo.java
java -cp out com.patterns.<分类>.<模式>.beginner.BeginnerDemo
```

## 3. 质量检查清单

写完一篇，逐条打勾：

- [ ] 第一屏没有角色表、UML、GoF 定义。
- [ ] 「改造前」代码能独立编译运行，问题能通过输出看见。
- [ ] 解释了谁依赖谁，而不是只说「耦合」。
- [ ] 每个新增抽象都回答了「不加会怎样」。
- [ ] 有一个最小版本，再逐步加结构，不是一次性给完整设计。
- [ ] 执行过程用了具体输入和真实输出。
- [ ] 新增需求的前后改动范围可对照。
- [ ] 写清了模式新增的成本，以及「什么时候不该用」。
- [ ] 与至少一个易混模式做了「问题不同」的对比。
- [ ] 练习题有场景判断 + 原因解释，答案是推导不是背诵。
- [ ] 没有把撤销、异步、持久化、线程安全等可选/外部能力说成模式必备。
- [ ] 深度文档链接有效，且没有删除原有内容。

## 4. 23 种模式的「不同故事」

入门材料最容易犯的错，是把 23 个模式都讲成「抽接口、加实现、多态调用」。
下表是每种模式**真正不同的设计动机**，写作时必须围绕它展开。

| # | 模式 | 入门场景 | 不用的具体痛点 | 关键抽象 | 最易混淆 |
|---|---|---|---|---|---|
| 1 | 单例 | 全局配置被反复 new | 多份状态不一致、重复加载 | 私有构造 + 唯一实例 | 静态工具类、全局变量 |
| 2 | 工厂方法 | 通知渠道创建散落多处 | 新增渠道改多个调用点 | 创建者子类决定产品 | 简单工厂、抽象工厂 |
| 3 | 抽象工厂 | 亮/暗主题的按钮+复选框 | 产品族被混搭、换主题改多处 | 一族产品的创建接口 | 工厂方法 |
| 4 | 建造者 | 7 个参数的 HTTP 请求 | 构造器爆炸、setter 留下非法中间态 | 分步构建 + build 校验 | 工厂、setter |
| 5 | 原型 | 复制带嵌套样式的文档模板 | 手写拷贝漏字段、浅拷贝串改 | copy 契约 + 深拷贝 | new、Cloneable |
| 6 | 适配器 | 老支付 SDK 与新接口 | 调用方被迫理解厂商单位/命名 | 转换接口的包装器 | 装饰器、代理、外观 |
| 7 | 桥接 | 消息类型 × 发送渠道 | 继承层级按维度相乘爆炸 | 抽出独立变化的维度 | 策略、适配器 |
| 8 | 组合 | 文件夹与文件统一统计 | 客户端 instanceof 递归、加节点类型改遍历 | 叶子和容器同一接口 | 装饰器 |
| 9 | 装饰器 | 咖啡加料/通知增强 | 组合爆炸、功能无法运行时叠加 | 同接口包装 + 委托 | 代理、继承 |
| 10 | 外观 | 电脑启动的多子系统顺序 | 调用方重复编排、漏步骤 | 一个稳定入口 | 中介者、适配器 |
| 11 | 享元 | 十万字符共享字体样式 | 大量重复的不可变数据占内存 | 内在状态共享 + 外在状态外传 | 单例、对象池、缓存 |
| 12 | 代理 | 报表权限校验 + 延迟加载 | 每个调用方重复鉴权/加载 | 同接口的控制对象 | 装饰器、适配器 |
| 13 | 责任链 | 分级审批 | 金额规则写死、加一级改方法 | 同类型后继节点 | 装饰器、策略 |
| 14 | 命令 | 夜间批处理调度 | 加任务改调度器、失败整批中断、无法重试/审计 | 请求对象 + 统一 execute | 策略、观察者、事件 |
| 15 | 解释器 | 可配置的优惠规则表达式 | 规则写死、每换规则改代码 | 表达式树 + interpret | 策略、访问者 |
| 16 | 迭代器 | 播放列表的多种遍历 | 暴露内部存储、换遍历改客户端 | 统一 hasNext/next | 组合、访问者 |
| 17 | 中介者 | 售后工单多方协作 | 同事互相持有，N×N 依赖 | 中心路由 + 同事只认中介 | 外观、观察者 |
| 18 | 备忘录 | 编辑器撤销 | 暴露内部状态、客户端管快照 | 不透明快照 + 管理者 | 命令撤销、原型 |
| 19 | 观察者 | 下单后多渠道通知 | 下单服务直接依赖所有通知方 | 主题注册 + 回调 | 中介者、发布订阅 |
| 20 | 状态 | 订单状态驱动可用操作 | 每个方法都写状态 if、非法流转 | 状态对象 + 委托 | 策略、状态机表 |
| 21 | 策略 | 结算折扣规则 | 加规则改结算方法、无法运行时替换 | 可替换算法 + 上下文 | 状态、模板方法 |
| 22 | 模板方法 | CSV/JSON 导入固定流程 | 流程重复、漏步骤、顺序不一致 | 父类骨架 + 子类步骤 | 策略、工厂方法 |
| 23 | 访问者 | 文档元素导出多种格式 | 加格式改所有元素类 | 双分派 + 操作外置 | 迭代器、策略 |

## 5. 写一篇新入门文档的流程

1. 先读该模式的工程版 `README.md` 和 `Client`，确认哪些是模式本身、哪些是项目扩展。
2. 想一个**没有这个模式就会疼**的最小业务，控制在 3～5 个类。
3. 先写 `BeginnerDemo.java` 的「改造前」，编译运行，把真实输出贴进文档。
4. 再写「改造后」，每加一个类都问「不加会怎样」。
5. 按八段式写 `BEGINNER.md`，最后补练习与深度链接。
6. 编译运行，核对文档输出；检查链接与代码围栏。
7. 用第 3 节清单自检，特别确认没有把可选能力写成必备。

## 6. 和深度层怎么衔接

入门文档结尾统一放这四类链接：

- 本模式深度文档：`README.md`
- 可运行工程版入口：`Client.java`（单例是 `SingletonClient.java`）
- 相关项目级文档：`docs/02-pattern-comparison.md`、`docs/06-modern-scenarios.md`
- 如果该模式出现在组合案例中：`combined/orderservice` 或 `combined/apigateway`

深度文档顶部加一行回链：

```markdown
> **第一次接触这个模式？** 先读 [BEGINNER.md](BEGINNER.md)（通俗入门），
> 再回来读这篇工程深度版。
```
